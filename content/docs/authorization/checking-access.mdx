---
title: Checking Access
description: The check APIs, explainable decisions, and the AuthZEN PDP endpoint.
---

However you model access — [RBAC](/docs/authorization/rbac),
[ReBAC](/docs/authorization/rebac) or [ABAC](/docs/authorization/abac) — the
enforcement pattern is the same: **check on the server before you act**, and ask
for an **explanation** when you need to understand a decision.

## The basic check

```ts title="server.ts"
const claims = await qeetid.sessions.verify(token);

const allowed = await qeetid.permissions.check({
  user: claims.userId!,
  tenant: claims.tenantId!,
  permission: "billing:write",
});

if (!allowed) throw new Response("Forbidden", { status: 403 });
```

By default a check returns just `{ "allowed": true | false }`.

## Explainable decisions

Use the SDK's dedicated `explain` method, or add `explain=true` to the HTTP
request. The response includes the **grant path** — every role, direct or
group-derived, that produced the answer:

```ts title="server.ts"
const explanation = await qeetid.permissions.explain({
  user: claims.userId!,
  tenant: claims.tenantId!,
  permission: "billing:write",
});
```

```bash title="Terminal"
curl --get "$QEETID_BASE_URL/v1/check" \
  -H "Authorization: ApiKey $QEETID_API_KEY" \
  --data-urlencode "user_id=$USER_ID" \
  --data-urlencode "tenant_id=$TENANT_ID" \
  --data-urlencode "permission=billing:write" \
  --data-urlencode "explain=true"
```

```json title="Response"
{
  "allowed": true,
  "paths": [
    {
      "permission": "billing:write",
      "granted_by": "role:admin",
      "via": "group:finance",
      "group_id": "3ca8c334-4537-4aa4-a6ea-a26e58d24a19",
      "role_id": "81b4e12c-2fa0-43e9-860b-12c77408f21e"
    }
  ]
}
```

- **RBAC** returns the roles/bindings that grant the permission (plus a `reason`
  on denial).
- **ReBAC** returns the root-to-leaf chain of relation tuples.
- **ABAC** returns which conditions passed and failed.

<Callout type="success">
  Explanations make access reviews auditable and debugging trivial: instead of
  reasoning about a policy in your head, you ask the engine and it shows its
  work.
</Callout>

## AuthZEN (standard PDP)

For policy-enforcement points that prefer a standard over a vendor API, Qeet ID
implements the OpenID **AuthZEN** evaluation endpoint:

```http
POST /tenants/{tenantID}/access/v1/evaluation
```

The SDK calls the versioned route under `/v1`. It routes by `resource.type` (a
`permission` resource hits RBAC; anything else is treated as a ReBAC `type:id`
+ relation), returns `{ "decision": true|false }`, and honours
`context.explain` for the same grant-path trace.

<Callout type="warn">
  Always enforce authorization **server-side**. There is no browser-facing
  "what can I do?" endpoint by design — drive UI affordances from your own state
  and let the server be the source of truth.
</Callout>

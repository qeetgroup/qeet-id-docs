---
title: Organizations & Multi-tenancy
description: How Qeet ID names and isolates each organization boundary.
---

An **organization** is the top-level isolation boundary in Qeet ID. The API,
database and token claims call the same boundary a **tenant**. These are two
names for one object, not nested resources.

Every user record, group, role, session and audit entry is scoped to an
organization ID, and a request can only operate inside the organization carried
by its credential.

## Why it matters

Modelling organizations from the start means you never have to re-architect to
serve a second customer. A solo app and a multi-customer SaaS use the same
primitives — the difference is how many organization boundaries exist.

<Callout type="info">
  Isolation is enforced in the application layer today, with a Postgres
  row-level-security (RLS) pilot in progress to push isolation into the database
  itself.
</Callout>

## Scoping requests

Authorization calls are scoped with the tenant ID embedded in the verified
session. Management operations still accept explicit tenant IDs where their
SDK signatures require them:

```ts title="server.ts"
const claims = await qeetid.sessions.verify(token);

// Use the verified tenant, never a tenant supplied by the browser.
const members = await qeetid.users.list({ tenant: claims.tenantId! });
```

See [sessions and tokens](/docs/concepts/sessions-and-tokens) for how that
tenant context is carried and verified.
